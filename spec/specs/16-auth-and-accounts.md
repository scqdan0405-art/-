# 16. 認証・アカウント管理(店舗アカウント/スタッフコード/管理者ロール/パスワード方針)

06(セキュリティ)の認可マトリクスを前提に、アカウントのライフサイクルと認証の詳細を確定する。
実装が曖昧に判断しないための正。矛盾したら本書と06が正。

## 16.1 アカウント種別(再掲+確定)

| 種別 | 認証方式 | 単位 | 識別情報 |
|---|---|---|---|
| 利用者 | アカウントレス(booking_token + OTP) | 予約 | booking_token |
| 店舗アカウント | Supabase Auth (email+password) | **1店舗=1アカウント(端末共有)** | `app_metadata: { role:'store', store_id:<uuid> }` |
| 管理者 | Supabase Auth (email+password) | 個人 | `app_metadata: { role:'admin' }` |

- role/store_id は **`app_metadata` のみ**に置く(ユーザー自身が変更可能な `user_metadata` は認可に使わない)
- 店舗アカウントのメールは店舗運用メール(例: `store-bt@koncochii.com`)。個人メールを使わない

## 16.2 店舗アカウントのライフサイクル

- **作成**: 管理者のみ(`/admin/stores` の店舗詳細から)。サーバー側で Supabase Admin API を使い、role/store_id を app_metadata に設定して作成
- **初回パスワード**: 自動生成(16文字英数記号)を管理者画面に1回だけ表示 → 店舗へ安全に伝達。**初回ログイン時にパスワード変更を強制**(`must_change_password` フラグを app_metadata に持ち、middleware で変更画面へリダイレクト)
- **無効化**: 管理者操作で Supabase の ban(`banned_until`)を設定 → 即時ログイン不可+既存セッション失効。`stores.is_active` とは独立(店舗を休止せずアカウントだけ止められる)
- **パスワードリセット**: ①店舗セルフ: 登録メール宛リセットリンク(Supabase標準) ②管理者強制リセット: 新初回パスワード発行(変更強制付き)
- **削除はしない**(audit_logs の actor 参照を保持)。不要になったら ban のまま残す

## 16.3 スタッフコード(個人コード)

目的: 認証の主体は店舗アカウント。スタッフコードは**行為者の識別(責任追跡)と操作ゲート**であり、単独では何の権限も持たない。

- 形式: **4桁数字**・店舗内一意(`unique(store_id, staff_code)`)。発行時に**自動生成**(`crypto.randomInt`。`0000`/`1234`等の弱い並び・既存/失効済みコードは再抽選)
- **発行**: 管理者のみ(`/admin/stores` のスタッフ管理)。表示名(実名 or ニックネーム)を必須入力
- **失効**: `is_active=false`(削除しない)。失効コードでの操作は403。**再有効化可**。**コードの使い回し(別人への再割当)は禁止**(失効済み行も unique 制約に残すことで担保)
- **利用**: 04のとおり操作の最初に入力→15分セッション保持(サーバー側セッションに保持。localStorage に置かない)。検証は毎APIで `x-staff-code` × staff テーブル照合(store_id は JWT 由来)
- コードはDB平文でよい(低機密。認証情報ではないため)。ただし画面・ログへの一覧表示は管理画面のみ

## 16.4 管理者ロール

- **付与/剥奪**: PoC では管理画面からのロール管理は**実装しない**。初期 admin は seed で作成し、追加・剥奪は運営が Supabase ダッシュボード(app_metadata 編集)で行う。**admin が常に1名以上残ることを運用ルールとする**
- admin は店舗APIを呼べない(06の認可マトリクスどおり。role='store' のみ)。店舗画面の確認が必要な場合は店舗アカウントでログインする
- **MFA(TOTP)**: admin は Supabase MFA を**有効化推奨**(PoCは任意、本番前に必須化)

## 16.5 パスワード方針(店舗・管理者共通)

- **最小12文字**・最大72文字(bcrypt上限)。文字種の強制はしない(長さ優先・NIST SP800-63B準拠)
- Supabase の **leaked password protection(漏洩パスワード拒否)を有効化**
- ログイン試行: **5回失敗/15分/メールアドレス** でロック(Supabase レート制限+必要なら簡易DB実装)。ロックは時間経過 or 管理者解除
- 使い回し検査・定期変更の強制はしない(NIST準拠。漏洩兆候時のみ強制リセット)

## 16.6 セッション

| 対象 | JWT有効期限 | refresh token | 備考 |
|---|---|---|---|
| 店舗 | 1時間 | **30日**(店舗端末で常用のため) | スタッフコード15分ゲートが操作単位の抑止 |
| 管理者 | 1時間 | **7日** | 共有端末での利用禁止(運用ルール) |

- ログアウトボタンを両画面に設置。ban 時は refresh 失敗で強制ログアウト

## 16.7 認可の実装ルール

- middleware: `/store/*` は `role='store'`、`/admin/*` は `role='admin'` を検証。**ロール不一致・未ログインは404**(存在秘匿。05の受入基準と整合)
- 店舗APIの store_id は **JWT の app_metadata.store_id を正**とする。リクエストボディ・クエリの店舗指定は信用しない
- `x-staff-code` 未入力/無効は403(04の受入基準どおり)。スタッフコードは認可判定に使わない(actor記録+ゲートのみ)

## 16.8 監査(audit_logs へ必須記録)

ログイン成功/失敗(store/admin) / パスワード変更・リセット / アカウント作成・ban / スタッフコード発行・失効・再有効化 / OTPロック解除・手動オーバーライド(06)。actor_type/actor_id/detail を記録。PII はログに出さない(06)。

## 16.9 受け入れ基準

- [ ] role なし・不一致のユーザーは /store・/admin 全ページ・全APIで404
- [ ] must_change_password の店舗アカウントは変更完了までどの画面にも進めない
- [ ] ban された店舗アカウントは既存セッションでも次のAPI呼び出しから拒否される
- [ ] 失効スタッフコードでの操作は403、audit_logs に記録される
- [ ] スタッフコード自動生成が弱い並び・重複を返さない(ユニットテスト)
- [ ] 11文字パスワードは登録・変更とも拒否される
